## 1. 项目总体采用什么架构？

**总体架构：插件化微服务架构 + 事件驱动架构 + 分层部署架构。**

具体包含五个层面：

| 层面     | 架构模式     | 说明                                  |
| -------- | ------------ | ------------------------------------- |
| 整体结构 | 插件化微服务 | 核心服务 + 插件，独立部署，独立演进   |
| 通信方式 | 事件驱动     | 服务之间通过消息总线通信，不直接调用  |
| 扩展方式 | 插件化       | 新增功能 = 新增插件目录 + plugin.json |
| 部署形态 | 分层部署     | 服务与层分离，层是配置，可单层可多层  |
| 前端形态 | 微前端       | 前端外壳 + 插件前端模块动态加载       |

**核心特征：**

- 核心服务每次全启，冻结维护。
- 插件按 profile 选择启动，自由迭代。
- 数据流单一：外部 → Ingest → 消息总线 → 业务服务 → 消息总线 → Data-Writer → 存储。
- 只有 Ingest 连外部，只有 Data-Writer 连库。
- 服务之间零直接调用，只通过消息总线。
- 消息总线可切换，不绑定 Kafka。

## 3. 是否将 Kafka 的压力减小了？怎么实现的？计划怎么说明的？

**是的，Kafka 的压力被显著减小。**

### 怎么实现的

| 方案         | 作用                                                                    |
| ------------ | ----------------------------------------------------------------------- |
| 主题分层     | raw / aggregated / events 三层分离，插件默认订阅 aggregated，不订阅 raw |
| 选择性订阅   | 插件声明 filter，只收需要的数据                                         |
| 共享消费者组 | 相似插件共享 groupId，减少扇出                                          |
| Redis 热路径 | 高频查询走 Redis，不压 Kafka                                            |
| 批量消费     | max.poll.records 调优                                                   |
| 按车辆分区   | 分区键为 vehicle_id，并行消费                                           |
| 插件懒订阅   | 未激活不占消费者名额                                                    |
| 总线可切换   | 按场景选 Kafka / Memory，未来可扩展 Pulsar / NATS / Redis               |

### 核心规则

- 新插件默认订阅 `telemetry.aggregated`，不订阅 `telemetry.raw`。
- 新插件默认从 Redis 读状态，不直接消费 Kafka。
- 新插件默认 `lazy: true`，只有明确需要常驻才设 `false`。
- 实时性 < 50ms 走 Redis Pub/Sub，不走 Kafka。
- 不同层、不同主题可以用不同总线。
- 切换总线只改配置，业务代码零改动。

### 计划怎么说明的

- 在计划书中，消息总线性能策略单独成章。
- 逐项说明每个方案的作用。
- 明确核心规则。
- 预留对比实验：以后压测时对比优化前后的 Kafka 消费速率、延迟、积压。

## 4. 插件是否即插即用？

**是的，插件完全即插即用。**

### 即插即用的具体表现

| 操作     | 需要做什么                           | 不需要做什么                     |
| -------- | ------------------------------------ | -------------------------------- |
| 新增插件 | 放目录 + 写 plugin.json + 写业务代码 | 不改核心、不改网关、不改前端外壳 |
| 删除插件 | 删目录 + 重建 registry               | 不改核心、不改网关、不改前端外壳 |
| 替换插件 | 放新目录 + 改 plugin.json            | 不改核心、不改其他插件           |
| 启用插件 | 改 profile                           | 不改代码                         |

### 新增插件的完整流程

1. 从 `plugins/_template/` 复制目录。
2. 修改 `plugin.json`（name、version、core: false、profile、routes、frontend 等）。
3. 写后端 `src/index.js`。
4. （可选）写前端 `web/index.tsx`。
5. （可选）写测试 `tests/插件名.*.test.js`。
6. （可选）写文档 `docs/插件名.V1.md`。
7. 运行 `make build-registry`。
8. 启动时按 profile 自动加载。

**核心代码零改动，网关零改动，前端外壳零改动。**

### 即插即用的技术支撑

| 机制                 | 作用                                        |
| -------------------- | ------------------------------------------- |
| plugin.json 声明     | 每个插件声明自己的依赖、路由、前端、profile |
| registry.json 预生成 | 启动时不扫文件系统，O(1) 加载               |
| plugin-host 自动装配 | 读取 registry，拓扑排序，加载插件           |
| 网关路由动态注入     | 插件启动后自动注册路由到 gateway            |
| 前端动态 import      | 插件前端模块按需加载，导航自动生成          |
| profile 过滤         | 不同场景启动不同插件组合                    |

## 5. 项目是否可以一键部署、一键启动？

**是的，支持一键部署和一键启动。**

| 命令                    | 作用                                                           |
| ----------------------- | -------------------------------------------------------------- |
| `make deploy`         | 构建所有镜像 + 启动基础设施 + 启动核心 + 启动默认 profile 插件 |
| `make build-registry` | 扫描插件生成 registry.json                                     |

| 命令                        | 作用                             |
| --------------------------- | -------------------------------- |
| `make start-core`         | 只启动核心（10 个服务）          |
| `make start PROFILE=core` | 启动核心 + core profile 插件     |
| `make start PROFILE=full` | 启动核心 + full profile 所有插件 |
| `make stop`               | 停止所有服务                     |
| `make restart`            | 重启所有服务                     |
| `make status`             | 查看所有服务状态                 |

### 一键测试

| 命令                      | 作用           |
| ------------------------- | -------------- |
| `make test`             | 全部测试       |
| `make test-unit`        | 只跑单元测试   |
| `make test-integration` | 只跑集成测试   |
| `make test-e2e`         | 只跑端到端测试 |
| `make test-coverage`    | 带覆盖率       |

### 启动流程（自动化）

```
1. 加载 registry.json                    (O(1))
2. 核心强制加入                           (固定 10 个)
3. 按 PROFILE 过滤插件                    (O(n))
4. 拓扑排序（根据 dependsOn）             (O(n+e))
5. 按层并行启动                           (并行)
6. 并行健康检查                           (并行)
7. 就绪后注册路由到 gateway               (O(n))
8. 前端外壳动态加载插件前端模块           (懒加载)
```

### 启动效率

| 场景         | 核心 | 插件 | 总时间 |
| ------------ | ---- | ---- | ------ |
| 只启核心     | 10   | 0    | ~12s   |
| core profile | 10   | 5    | ~18s   |
| full profile | 10   | 15   | ~30s   |

**核心恒定 12 秒，插件再多只影响附加部分。**

## 6. 如果新增核心功能，是否要做巨大改动？

**结论：分三种情况，绝大部分不需要巨大改动。**

| 情况             | 示例                    | 改动范围                               | 是否巨大 |
| ---------------- | ----------------------- | -------------------------------------- | -------- |
| 扩展已有核心服务 | ingest 新增订阅一个主题 | 只改 ingest 内部                       | 不巨大   |
| 新增一个核心服务 | 新增 data-aggregator    | 新增目录 + plugin.json + 注册表 + 编排 | 中等     |
| 改动核心契约     | 改主题命名、改表结构    | 影响所有服务和插件                     | 巨大     |

### 为什么"扩展已有核心服务"不巨大

核心服务设计时已经预留了扩展点：

- ingest：主题列表从配置读，新增主题只改配置。
- data-writer：表映射从配置读，新增表只改配置。
- dispatch-core：算法在插件，替换算法只改插件。
- libs：封装层，新增工具只加文件，不改已有接口。

### 为什么"新增一个核心服务"是中等改动

新增核心服务需要：

- 在 `core/services/` 下新建目录。
- 写 `plugin.json`，标记 `core: true`。
- 写业务代码、测试、文档。
- 重建 `registry.json`。
- 在 `docker-compose.yml` 增加服务声明。

**不动已有核心服务的代码，不改 Kafka 主题契约，不改数据库表结构，不改 plugin.json 规范。**

### 为什么"改动核心契约"是巨大改动

如果改的是 Kafka 主题命名、数据库表结构、plugin.json 规范、registry.json 格式、前端插件加载协议，受影响的是核心服务、已有插件、测试、文档、前端外壳。

**这类改动才是真正的巨大改动。所以核心契约要稳定，核心要冻结。**

## 7. 新增插件，是否要修改与新增插件文件夹外的原有文件？

**结论：严格意义上只需要"重建 registry.json"这一个动作，但实际落地时，有两处需要提前设计好，否则会破功。**

### 理想情况（零改动）

新增插件的动作：

| 步骤 | 动作                             | 是否在插件文件夹外       |
| ---- | -------------------------------- | ------------------------ |
| 1    | 新建`plugins/新插件/` 目录     | 否                       |
| 2    | 写`plugin.json`                | 否                       |
| 3    | 写后端`src/index.js`           | 否                       |
| 4    | 写前端`web/index.tsx`（可选）  | 否                       |
| 5    | 写测试`tests/新插件.*.test.js` | 是（新增文件，不改已有） |
| 6    | 写文档`docs/新插件.V1.md`      | 是（新增文件，不改已有） |
| 7    | 运行`make build-registry`      | 是（重建 registry.json） |
| 8    | 启动                             | 是（用 make start）      |

**核心、网关、前端外壳、其他插件：零改动。**

### 两个必须提前设计好的点

**问题一：docker-compose.yml 不能硬编码插件。**

如果 docker-compose.yml 里写死了每个插件，那新增插件就必须改 docker-compose.yml。解决方案：由 plugin-host 动态启动插件，不在 docker-compose.yml 里声明插件。

**问题二：前端外壳不能硬编码插件路由。**

如果前端外壳写死了每个插件的路由，那新增插件就必须改前端外壳。解决方案：前端路由由插件注册表动态生成。

### 如果这两点没设计好，会发生什么

| 没设计好的点                  | 后果                 |
| ----------------------------- | -------------------- |
| docker-compose.yml 硬编码插件 | 新增插件要改编排文件 |
| 前端外壳硬编码路由            | 新增插件要改前端代码 |
| 网关硬编码路由                | 新增插件要改网关配置 |
| registry.json 手工维护        | 新增插件要手工改索引 |

**只要有一个破功，就不是真正的即插即用。**

## 8. 如果 Kafka 压力实在太大怎么办？这个架构能扛得住吗？

**结论：能扛住。分四层递进解决。**

### 第一层：消费侧优化

| 方案       | 做法                         | 效果             |
| ---------- | ---------------------------- | ---------------- |
| 消费者合并 | 多个插件合并为一个消费者进程 | 组数从 N 降到 1  |
| 批量处理   | 一次处理一批消息             | 吞吐提升 5-10 倍 |
| 异步提交   | 手动异步提交 offset          | 减少 rebalance   |
| 消费者限流 | 控制拉取速率                 | 防慢消费者拖累   |
| 多线程消费 | 一个消费者进程多线程处理     | 利用多核         |

### 第二层：状态查询移出 Kafka

| 方案                | 做法                   | 效果             |
| ------------------- | ---------------------- | ---------------- |
| Redis 全量热路径    | 所有状态查询走 Redis   | Kafka 只做事件流 |
| PostgreSQL 只读副本 | 复杂查询走只读副本     | 主库不受影响     |
| 本地缓存            | 插件本地缓存热点数据   | 减少 Redis 压力  |
| CQRS                | 写路径和读路径彻底分离 | 各自独立扩展     |

**目标：Kafka 只负责"事件流"，不负责"状态查询"。**

### 第三层：消息总线分片

| 方案           | 做法                       | 效果         |
| -------------- | -------------------------- | ------------ |
| 按业务分集群   | 遥测一个集群，告警一个集群 | 各自独立扩展 |
| 按区域分集群   | 华东一个集群，华北一个集群 | 地理分片     |
| 按优先级分集群 | 实时一个集群，批量一个集群 | 优先级隔离   |

### 第四层：换总线或引入新总线

| 场景               | 换什么               | 为什么                 |
| ------------------ | -------------------- | ---------------------- |
| 实时性要求 < 10ms  | Redis Pub/Sub        | Kafka 最低延迟是几毫秒 |
| 超高频、允许丢消息 | NATS / Redis Streams | 更轻量                 |
| 超大吞吐、流处理   | Pulsar               | 存算分离，扩展性更强   |
| 冷数据             | S3/MinIO             | 低成本、长期           |
| 设备侧消息         | MQTT 直连            | 不经过 Kafka           |

**架构上，Kafka 不是唯一选择，而是"温路径"的选择。热路径走 Redis Pub/Sub，冷路径走对象存储，温路径走 Kafka。消息总线抽象层支持切换，只改配置。**

### 边界

有些能力是媒介特有的，抽象层抹不平：

| 能力     | 处理                                 |
| -------- | ------------------------------------ |
| 事务     | 抽象层不暴露，特殊需求直接用原生 SDK |
| 精确一次 | 抽象层降级为至少一次 + 去重          |
| 全局有序 | 抽象层不承诺                         |
| 流处理   | 不抽象，作为独立能力                 |

## 9. 是否能做到数据流流向统一，数据流不依赖某个媒介传递？

**是的，能做到。**

### 数据流统一

| 维度       | 统一规则                                     |
| ---------- | -------------------------------------------- |
| 出入口统一 | 只有 Ingest 连外部，只有 Data-Writer 连存储  |
| 流向统一   | 外部 → 入口 → 总线 → 业务 → 总线 → 存储 |
| 契约统一   | 所有消息用同一套格式定义                     |
| 抽象统一   | 所有服务只依赖 MessageBus 接口               |
| 切换统一   | 改配置`MESSAGE_BUS=xxx` 即可               |

### 不依赖单一媒介

| 场景       | 做法                             |
| ---------- | -------------------------------- |
| 演示环境   | 用 Memory 适配器，不需要真实总线 |
| 当前阶段   | 用 Kafka，成熟                   |
| 未来扩展   | 用 Pulsar，存算分离              |
| 低延迟场景 | 用 NATS，微秒级                  |
| 外部接入   | 用 MQTT，长连接                  |

**同一套数据流，不同场景选不同媒介，业务代码不变。**

### 怎么做到

| 层次             | 解耦方式                                         |
| ---------------- | ------------------------------------------------ |
| 消息总线抽象     | 业务代码只依赖统一接口                           |
| 数据流声明独立   | 数据流定义在配置里，不写在代码里                 |
| 媒介绑定在部署层 | 数据流定义好之后，具体用哪个媒介在部署配置里决定 |
| 数据流与媒介解耦 | 数据流稳定，媒介可替换                           |

## 10. 功能是否独立于数据流存在？

**是的，功能独立于数据流存在。**

### 核心思想

**功能定义"做什么"，数据流定义"数据怎么来、怎么去"。**

| 概念   | 定义             | 举例                           |
| ------ | ---------------- | ------------------------------ |
| 功能   | 业务逻辑，做什么 | 最近邻调度、围栏检测、异常判断 |
| 数据流 | 数据的来源和去向 | 从遥测主题消费，向命令主题生产 |

**功能不关心数据从哪来、到哪去；数据流不关心数据被怎么处理。**

### 怎么做到

| 层次                 | 做法                               |
| -------------------- | ---------------------------------- |
| 功能定义输入输出接口 | 功能只依赖 IInput / IOutput 接口   |
| 数据流层做适配       | 数据流层把真实数据源适配到功能接口 |
| 功能可以独立测试     | 传入 Mock IInput，验证 IOutput     |
| 功能可以独立部署     | 换数据源只换适配器，功能不变       |

### 在项目中的体现

| 组件          | 功能         | 数据流                                         |
| ------------- | ------------ | ---------------------------------------------- |
| dispatch-core | 最近邻算法   | 从 telemetry.raw 消费，向 events.commands 生产 |
| geofence      | 围栏判断     | 从 telemetry.raw 消费，向 events.alerts 生产   |
| anomaly       | 阈值检测     | 从 telemetry.raw 消费，向 events.alerts 生产   |
| simulator     | 车辆状态模拟 | 向 MQTT 生产                                   |
| data-writer   | 数据持久化   | 从总线消费，向 PG/Redis 写                     |

**每个组件的功能独立于它的数据流配置。**

### 边界

功能独立于数据流的"实现"，但依赖数据流的"能力"：

- 功能有频率要求 → 需要高频数据流。
- 功能有延迟要求 → 需要低延迟数据流。
- 功能有一致性要求 → 需要支持事务的数据流。

## 11. 层是否与服务分离？

**是的，层与服务完全分离。**

### 核心思想

**服务是逻辑单元，层是部署单元。同一服务可以在任意层部署，代码不变。**

| 概念     | 定义                                            |
| -------- | ----------------------------------------------- |
| 服务     | 逻辑功能，如 dispatch-core、ingest、data-writer |
| 层       | 部署位置，如接入层、处理层、决策层              |
| 服务实例 | 服务在某一层的具体运行实例                      |
| 层配置   | 声明某层启用哪些服务                            |

### 服务与层的关系

| 服务          | 接入层 | 处理层 | 决策层 |
| ------------- | ------ | ------ | ------ |
| ingest        | ✅     | ✅     | ✅     |
| data-writer   | ✅     | ✅     | ✅     |
| dispatch-core | ✅     | ✅     | ✅     |
| observability | ✅     | ✅     | ✅     |
| registry      | ✅     | ✅     | ✅     |

**同一服务在每层以不同配置运行，代码一份。**

### 层配置

```yaml
layers:
  - name: access
    services: [ingest, data-writer, dispatch-core, observability, registry]
  - name: processing
    services: [ingest, data-writer, dispatch-core, observability, registry]
  - name: decision
    services: [ingest, data-writer, dispatch-core, observability, registry]
```

**层只决定启用哪些服务，服务代码不变。**

### 加层

后续要加层，只需在 `layers.yml` 中插入一段配置，服务代码零改动：

```yaml
layers:
  - name: access
    services: [...]
  - name: region          # 新加
    services: [...]
  - name: processing
    services: [...]
  - name: decision
    services: [...]
```

**加层只加配置，服务代码零改动。**

### 分离的好处

| 好处       | 说明                               |
| ---------- | ---------------------------------- |
| 加层零改动 | 层是配置，服务代码不变             |
| 部署灵活   | 同一服务可在任意层部署             |
| 独立演进   | 层演进不影响服务，服务演进不影响层 |
| 独立测试   | 服务测试不需要层环境               |

## 14. 在什么情况下要改动核心契约？

**核心契约 = 服务之间、服务与插件之间、插件与前端之间的约定。改核心契约是巨大改动，要尽量避免。**

### 核心契约包括什么

| 契约 | 内容 |
|---|---|
| 消息格式 | Kafka 消息的字段、结构、类型 |
| 主题命名 | telemetry.raw、events.commands 等 |
| 数据库表结构 | vehicle_latest、vehicle_telemetry、alerts |
| plugin.json 规范 | 插件声明的字段、格式 |
| registry.json 格式 | 注册表的结构 |
| API 接口 | 服务的 HTTP 接口 |
| 前端插件协议 | 前端模块的导出格式 |
| 层配置格式 | layers.yml 的结构 |

### 什么情况下要改核心契约

| 情况 | 改什么 | 是否必须 |
|---|---|---|
| 新增业务字段 | 消息格式加字段 | 必须，但可兼容 |
| 修改业务字段 | 消息格式改字段 | 必须，但不兼容 |
| 删除业务字段 | 消息格式删字段 | 必须，但不兼容 |
| 新增主题 | 主题命名加一个 | 必须，但可兼容 |
| 修改主题命名 | 主题命名改一个 | 必须，但不兼容 |
| 新增数据库表 | 表结构加一个 | 必须，但可兼容 |
| 修改数据库表 | 表结构改一个 | 必须，但不兼容 |
| 新增插件字段 | plugin.json 加字段 | 必须，但可兼容 |
| 修改插件字段 | plugin.json 改字段 | 必须，但不兼容 |
| 新增 API | API 加一个 | 必须，但可兼容 |
| 修改 API | API 改一个 | 必须，但不兼容 |
| 新增前端导出 | 前端协议加字段 | 必须，但可兼容 |
| 修改前端导出 | 前端协议改字段 | 必须，但不兼容 |

### 改核心契约的两种类型

**类型一：兼容性改动（不巨大）**

| 改动 | 影响 |
|---|---|
| 消息格式加字段 | 旧服务忽略新字段，不影响 |
| 新增主题 | 旧服务不订阅，不影响 |
| 新增数据库表 | 旧服务不查询，不影响 |
| plugin.json 加可选字段 | 旧插件不声明，不影响 |
| 新增 API | 旧客户端不调用，不影响 |
| 前端协议加可选字段 | 旧插件不导出，不影响 |

**兼容性改动的影响范围小，不需要所有服务和插件同时改。**

**类型二：破坏性改动（巨大）**

| 改动 | 影响 |
|---|---|
| 消息格式改字段名 | 所有消费该主题的服务和插件都要改 |
| 消息格式改字段类型 | 同上 |
| 消息格式删字段 | 同上 |
| 主题命名改名 | 所有生产和消费该主题的服务和插件都要改 |
| 数据库表结构改字段 | 所有查询该表的服务和插件都要改 |
| plugin.json 改必填字段 | 所有插件都要改 |
| registry.json 改格式 | 所有生成和使用注册表的工具都要改 |
| API 改接口 | 所有调用该 API 的客户端都要改 |
| 前端协议改必填字段 | 所有前端插件都要改 |
| 层配置改格式 | 所有层配置都要改 |

**破坏性改动的影响范围大，需要所有相关方同步改。**

### 怎么避免破坏性改动

| 策略 | 做法 |
|---|---|
| 兼容优先 | 新增字段而非改字段；新增主题而非改主题 |
| 版本化 | 契约有版本，新旧版本共存 |
| 废弃周期 | 旧契约保留至少 2 个版本 |
| 适配层 | 如需大改，先加适配层，旧接口保留 |
| 契约冻结 | 核心契约一旦定下，不轻易改 |
| 扩展优先 | 新需求优先用插件实现，而非改核心契约 |

### 什么时候必须改核心契约

| 情况 | 必须改 |
|---|---|
| 业务模型根本性变化 | 是 |
| 法规要求变化 | 是 |
| 性能瓶颈无法通过扩展解决 | 是 |
| 安全漏洞无法通过补丁解决 | 是 |
| 技术栈根本性升级 | 是 |

**除了这些，绝大多数需求都可以通过“加插件、加字段、加主题”解决，不需要改核心契约。**

### 结论

| 问题 | 回答 |
|---|---|
| 什么情况下要改核心契约 | 业务模型根本性变化、法规变化、性能瓶颈、安全漏洞、技术栈升级 |
| 改核心契约是否巨大 | 兼容性改动不巨大，破坏性改动巨大 |
| 怎么避免 | 兼容优先、版本化、废弃周期、适配层、契约冻结、扩展优先 |

## 15. 如果 Kafka 压力实在太大怎么办？四层递进方案实现起来方便吗？

**结论：四层递进方案，前两层方便，第三层中等，第四层部分方便部分不方便。整体可以实现，但越往后越重。**

### 四层递进方案回顾

| 层次 | 方案 | 解决问题 |
|---|---|---|
| 第一层 | 消费侧优化 | 消费慢、rebalance 频繁 |
| 第二层 | 状态查询移出 Kafka | Kafka 被查询压垮 |
| 第三层 | 消息总线分片 | 单集群扛不住 |
| 第四层 | 换总线或引入新总线 | Kafka 不适合某些场景 |

### 第一层：消费侧优化——方便

| 方案 | 实现方式 | 是否方便 |
|---|---|---|
| 消费者合并 | 改消费者配置 | 方便 |
| 批量处理 | 改 max.poll.records | 方便 |
| 异步提交 | 改 offset 提交方式 | 方便 |
| 消费者限流 | 改拉取速率配置 | 方便 |
| 多线程消费 | 改消费者内部实现 | 中等 |

**整体评价：方便。大部分是配置改动，少量是代码改动。**

**前提：** 消息总线抽象层已预留批量消费、异步提交接口。

### 第二层：状态查询移出 Kafka——中等

| 方案 | 实现方式 | 是否方便 |
|---|---|---|
| Redis 全量热路径 | 加 Redis 写入 + 查询逻辑 | 中等 |

| CQRS | 写路径和读路径彻底分离 | 不方便 |

**整体评价：中等。需要改 data-writer 加 Redis 写入，改查询服务加 Redis 读取，但不改核心契约。**

**前提：** 数据流设计已预留 Redis 热路径。

### 第三层：消息总线分片——不方便

| 方案 | 实现方式 | 是否方便 |

| 按业务分集群 | 改部署架构，加多集群 | 不方便 |

| 按优先级分集群 | 改部署架构，加多集群 | 不方便 |

**整体评价：不方便。需要改部署架构，加多集群，改连接配置，改监控，改运维。**

**为什么不方便：**
- 需要多套 Kafka 集群。
- 需要跨集群消息路由。
- 需要跨集群监控。
- 需要跨集群运维。
- 需要跨集群一致性。

**前提：** 消息总线抽象层支持多实例，部署架构支持多集群。

### 第四层：换总线或引入新总线——部分方便部分不方便

| 场景 | 实现方式 | 是否方便 |

**整体评价：换总线方便（抽象层已预留），引入新总线中等（需要数据流分段）。**

**前提：** 消息总线抽象层已预留多适配器接口。

### 四层递进方案的整体评价

| 层次 | 方便程度 | 主要工作 | 是否改核心契约 |
|---|---|---|---|
| 第一层 | 方便 | 改配置 + 少量代码 | 不改 |

| 问题 | 回答 |
|---|---|
| 四层递进方案能实现吗 | 能 |
| 实现起来方便吗 | 前两层方便，第三层重，第四层部分方便 |
| 需要改核心契约吗 | 不需要 |
| 需要重构吗 | 不需要 |
| 前提是什么 | 消息总线抽象层、Redis 热路径、多适配器接口已预留 |
| 建议 | 按需启动，不要一次性全做 |

## 16. 我的项目结构可以有多集群吗？

**结论：可以，项目结构已经为多集群预留了基础，但多集群的落地需要额外设计。**

### 16.1 项目结构中的哪些设计支持多集群

| 设计 | 如何支持多集群 |
|---|---|
| 服务与层分离 | 同一服务可以在多个集群部署，代码一份 |
| 消息总线抽象 | 每个集群可以用不同的总线，配置不同 |
| 层配置驱动 | 每层可以对应一个集群，层配置决定集群 |
| 部署配置化 | 支持按层组合部署，每层可独立部署 |
| 契约优先 | 多集群共享契约，数据格式一致 |
| 插件化 | 每个集群可以按需启用不同插件 |

### 16.2 多集群的形态

| 形态 | 说明 | 适用场景 |
|---|---|---|
| 按业务分集群 | 遥测一个集群，告警一个集群，命令一个集群 | 业务隔离 |
| 按区域分集群 | 华东一个集群，华北一个集群 | 地理分片 |
| 按层分集群 | 接入层一个集群，处理层一个集群，决策层一个集群 | 层间隔离 |
| 按租户分集群 | 每个租户独立集群 | 多租户隔离 |
| 混合分集群 | 按业务 + 区域组合 | 复杂场景 |

### 16.3 项目结构支持多集群的方式

**方式一：层配置对应集群**

```yaml
layers:
  - name: access-east
    cluster: east
    services: [ingest, data-writer, dispatch-core, observability, registry]
  - name: access-west
    cluster: west
    services: [ingest, data-writer, dispatch-core, observability, registry]
  - name: decision
    cluster: center
    services: [dispatch-core, observability, registry]
```

**方式二：消息总线配置对应集群**

```yaml
messageBus:
  east:
    type: kafka
    brokers: [east-kafka:9092]
  west:
    type: kafka
    brokers: [west-kafka:9092]
  center:
    type: kafka
    brokers: [center-kafka:9092]
```

**方式三：部署配置对应集群**

```
deploy/
├── cluster-east/
│   ├── docker-compose.yml
│   └── layers.yml
├── cluster-west/
│   ├── docker-compose.yml
│   └── layers.yml
└── cluster-center/
    ├── docker-compose.yml
    └── layers.yml
```

### 16.4 多集群需要额外设计什么

| 需要设计 | 说明 |
|---|---|
| 跨集群消息路由 | 一个集群的消息如何到另一个集群 |
| 跨集群一致性 | 多集群数据如何保持一致 |
| 跨集群查询 | 查询如何路由到对应集群 |
| 跨集群监控 | 多集群指标如何聚合 |
| 跨集群追踪 | 跨集群调用链如何追踪 |
| 跨集群故障切换 | 一个集群故障，如何切换到另一个 |
| 跨集群版本管理 | 多集群版本如何管理 |
| 跨集群部署 | 多集群如何统一部署 |

**这些设计当前没有，但项目结构预留了扩展点。**

### 16.5 多集群的边界

| 边界 | 说明 |
|---|---|
| 不能共享状态 | 多集群之间状态独立，最终一致 |
| 不能强一致 | 跨集群强一致代价高，通常用最终一致 |
| 不能共享事务 | 跨集群事务代价高，通常用补偿 |
| 不能共享连接 | 每个集群独立连接自己的总线、数据库 |
| 不能共享缓存 | 每个集群独立缓存 |

### 16.6 多集群的落地路径

| 阶段 | 集群数 | 说明 |
|---|---|---|
| 当前 | 1 | 单集群 |
| 压力初现 | 2 | 按业务分两个集群 |
| 压力加大 | 3-5 | 按区域分多个集群 |
| 规模很大 | 10+ | 按区域 + 业务组合 |
| 超大规划 | 数十个 | 多集群 + 多活 |

### 16.7 结论

| 问题 | 回答 |
|---|---|
| 项目结构可以有多集群吗 | 可以，结构已预留 |
| 当前是否多集群 | 否，当前单集群 |
| 多集群需要额外设计吗 | 需要，跨集群路由、一致性、监控、追踪、故障切换 |
| 多集群落地方便吗 | 加集群方便，跨集群协同不方便 |
| 建议 | 先单集群，压力到了再加集群 |

## 17. 层数的扩展有什么作用？

**结论：层数扩展的核心作用是“逐层聚合、数据衰减、就近处理、独立扩展、容错隔离”。层数越多，中心压力越小，但延迟和运维复杂度越高。**

### 17.1 层数扩展的六大作用

**作用一：数据逐层聚合，中心压力指数级降低**

| 层数 | 数据量 | 中心压力 |
|---|---|---|
| 1 层 | 全部原始数据 | 100% |
| 2 层 | 车端原始 → 边缘摘要 | 1% |
| 3 层 | 车端原始 → 边缘摘要 → 区域摘要 | 0.01% |
| 4 层 | 车端原始 → 边缘 → 区域 → 中心 | 0.0001% |

**每加一层，数据衰减 100:1。1000 万辆车经过三层聚合，中心只处理 10 条/秒。**

**作用二：就近处理，延迟低**

| 场景 | 单层 | 多层 |
|---|---|---|
| 车辆状态查询 | 中心查询，跨网络 | 就近查询，本地响应 |
| 区域调度 | 中心决策 | 边缘决策 |
| 紧急任务 | 中心下发 | 边缘下发 |

**就近处理降低延迟，提升响应速度。**

**作用三：独立扩展，哪层压力大扩展哪层**

| 层 | 压力来源 | 扩展方式 |
|---|---|---|
| 接入层 | 车辆连接数多 | 加接入节点 |
| 处理层 | 数据处理量大 | 加处理节点 |
| 决策层 | 全局调度复杂 | 加决策节点 |

**每层独立扩展，互不影响。**

**作用四：容错隔离，一层故障不影响其他层**

| 故障 | 单层 | 多层 |
|---|---|---|
| 接入层故障 | 整个系统不可用 | 处理层、决策层继续工作 |
| 处理层故障 | 整个系统不可用 | 接入层缓存数据，恢复后补传 |
| 决策层故障 | 整个系统不可用 | 处理层独立工作 |
| 网络分区 | 整个系统不可用 | 各层独立工作，恢复后同步 |

**层数越多，容错能力越强。**

**作用五：数据本地化，满足合规要求**

| 合规要求 | 单层 | 多层 |
|---|---|---|
| 数据本地存储 | 全部数据在中心 | 数据按区域存储 |
| 数据本地处理 | 全部在中心处理 | 数据在本地处理 |
| 数据不出境 | 难以保证 | 按区域隔离 |

**多层架构天然支持数据本地化。**

**作用六：按需部署，小规模用小架构，大规模用大架构**

| 规模 | 层数 | 说明 |
|---|---|---|
| 500 辆 | 1 层 | 单层足够 |
| 5000 辆 | 1-2 层 | 单层或双层 |
| 10 万 | 2-3 层 | 双层或三层 |
| 100 万 | 3-4 层 | 三层或四层 |
| 1000 万 | 4-5 层 | 四层或五层 |

**同一套代码，不同规模部署不同层数。**

### 17.2 层数扩展的代价

| 代价 | 说明 |
|---|---|
| 延迟增加 | 每层引入 50-200ms |
| 运维复杂度 | 层数越多，运维越复杂 |
| 调试难度 | 跨层问题难定位 |
| 一致性 | 层间最终一致，非强一致 |
| 成本 | 每层都要部署、监控、维护 |

**加层是权衡：数据量减少 vs 延迟增加。**

### 17.3 层数扩展的具体收益对比

| 维度 | 1 层 | 2 层 | 3 层 | 4 层 |
|---|---|---|---|---|
| 中心数据量 | 100% | 1% | 0.01% | 0.0001% |
| 中心压力 | 极大 | 大 | 中 | 小 |
| 延迟 | 低 | 中 | 中高 | 高 |
| 容错 | 低 | 中 | 高 | 极高 |
| 运维复杂度 | 低 | 中 | 高 | 极高 |
| 成本 | 低 | 中 | 高 | 极高 |
| 适用规模 | 小 | 中 | 大 | 超大 |

### 17.4 层数扩展与项目阶段的关系

| 阶段 | 层数 | 目的 |
|---|---|---|
| 当前阶段 | 1 层 | 跑通闭环，验证功能 |
| 规模初现 | 2 层 | 边缘聚合，降低中心压力 |
| 规模扩大 | 3 层 | 区域聚合，进一步降低中心压力 |
| 大规模 | 4 层 | 中心只处理全局事件和摘要 |
| 超大规划 | 5+ 层 | 按大区、城市细分 |

**每加一层都有明确目的，不是为加而加。**

### 17.5 层数扩展与业务的关系

| 业务需求 | 需要几层 | 理由 |
|---|---|---|
| 实时监控 | 1-2 层 | 数据量小，单层够 |
| 区域调度 | 2-3 层 | 需要区域级决策 |
| 全局调度 | 3-4 层 | 需要全局视图 |
| 跨区域协调 | 4 层 | 需要跨区域协同 |
| 多租户隔离 | 按租户分层 | 每租户独立 |
| 数据本地化 | 按地理分层 | 数据本地存储 |
| 容灾备份 | 按灾备分层 | 主备独立 |

### 17.6 层数扩展的边界

| 边界 | 说明 |
|---|---|
| 层数不是越多越好 | 每层都有成本，收益递减 |
| 延迟有下限 | 每层有固有延迟，层数多了延迟高 |
| 一致性有代价 | 层间一致性越难保证 |
| 运维有上限 | 层数多了运维跟不上 |
| 团队有上限 | 层数多了需要更多团队 |

**推荐层数：按规模选，不按理想选。**

### 17.7 结论

| 问题 | 回答 |
|---|---|
| 层数扩展有什么作用 | 数据聚合、就近处理、独立扩展、容错隔离、数据本地化、按需部署 |
| 层数越多越好吗 | 不是，每层有代价，收益递减 |
| 什么时候加层 | 规模上来了，单层扛不住时加 |
| 加层方便吗 | 方便，改配置即可，代码零改动 |
| 当前需要几层 | 1 层，跑通闭环 |
| 未来扩展 | 按规模加，2 层、3 层、4 层 |

### 17.8 一句话总结

**层数扩展的核心作用是“逐层聚合、数据衰减、就近处理、独立扩展、容错隔离”。每加一层，中心数据量衰减 100 倍，但延迟和运维成本增加。层数不是越多越好，而是按规模选。当前 1 层跑通闭环，未来按需扩展到 2 层、3 层、4 层。服务与层分离，加层零改动。**
