
# **ApisCloud - 蜂云**：智能驾驶服务调度系统 · 项目计划书

---

## 一、项目总目标

构建一套面向千万级智能驾驶车辆的服务调度系统，满足以下总目标：

| 编号 | 总目标       | 达成标准                                         |
| ---- | ------------ | ------------------------------------------------ |
| 1    | 系统可运行   | 500 辆模拟车辆实时调度，数据从采集到展示闭环     |
| 2    | 系统可扩展   | 新增功能只需新增插件，核心代码零改动             |
| 3    | 系统可维护   | 核心稳定冻结，插件自由迭代                       |
| 4    | 系统可观测   | 监控、日志覆盖插件、服务、数据流                 |
| 5    | 系统可测试   | 单元/集成/端到端三层测试覆盖                     |
| 6    | 系统可文档化 | 每个功能一个文档，记录版本演进                   |
| 7    | 系统可解耦   | 消息总线可切换，数据流不依赖单一媒介             |
| 8    | 系统可演进   | 从 500 辆模拟到千万级真实车辆，架构不推翻        |
| 9    | 调度可多维   | 支持多种调度算法，覆盖空间、服务等级等维度       |
| 10   | 插件可内嵌   | 插件支持进程内扩展，降低部署与运维复杂度         |
| 11   | 工程可自动化 | 具备 CI/CD 流水线，支持自动测试、自动构建        |
| 12   | 安全可内建   | 从认证、输入验证、密钥管理建立安全基础           |
| 13   | 压测可预留   | 当前不做压力测试，但预留监控、日志、配置可调能力 |

## 二、系统定位

本系统是**智能驾驶服务调度平台**，不是传统出租车调度，也不造自动驾驶系统，不控制车辆。

**核心定位：接入外部自动驾驶系统上报的数据，处理后做调度决策，下发指令给外部系统。**

| 维度     | 本系统                                           |
| -------- | ------------------------------------------------ |
| 我们做   | 接入数据、处理数据、调度决策、下发指令           |
| 我们不做 | 不采集原始传感器数据、不控制车辆、不负责车辆安全 |
| 对接对象 | 外部自动驾驶系统                                 |
| 调度对象 | 智能驾驶车辆                                     |
| 调度目标 | 调度智能驾驶服务任务                             |
| 车辆规模 | 千万级                                           |
| 服务类型 | 载客、巡检、物流、充电、维护、救援等             |
| 实时性   | 毫秒级到秒级                                     |
| 安全要求 | 极高（调度指令签名与校验）                       |

**核心差异：我们是调度平台，不是自动驾驶系统。**

## 三、接入与指令设计

### 3.1 接入数据分类

接入层要接的是外部自动驾驶系统上报的数据，按用途分五类：

| 类别     | 内容                               | 频率           |
| -------- | ---------------------------------- | -------------- |
| 车辆状态 | 位置、速度、航向、电量、状态、能力 | 高频（1-10Hz） |
| 任务请求 | 起点、终点、时间窗、类型、优先级   | 低频（按需）   |
| 环境数据 | 路况、天气、事件、拥堵             | 中频（1-60s）  |
| 心跳     | 在线状态、健康状态                 | 低频（10-60s） |
| 事件     | 异常、告警、完成、取消             | 事件驱动       |

### 3.2 指令数据分类

| 指令类型   | 内容                 | 方向             |
| ---------- | -------------------- | ---------------- |
| 调度指令   | 车辆去某地执行某任务 | 平台 → 外部系统 |
| 取消指令   | 取消某任务           | 平台 → 外部系统 |
| 重定位指令 | 车辆前往某区域待命   | 平台 → 外部系统 |
| 充电指令   | 车辆前往充电桩       | 平台 → 外部系统 |
| 维护指令   | 车辆前往维护站       | 平台 → 外部系统 |
| 紧急指令   | 紧急优先级任务       | 平台 → 外部系统 |
| 查询指令   | 查询车辆状态         | 平台 → 外部系统 |

### 3.3 接入协议设计

| 要点     | 说明                                |
| -------- | ----------------------------------- |
| 协议无关 | 支持 MQTT/gRPC/HTTP，按合作方能力选 |
| 契约优先 | 先定 Schema，再定传输               |
| 版本化   | 契约有版本，兼容旧版本              |
| 可扩展   | 新字段可加，不破坏旧版本            |
| 可校验   | 接入层校验数据合法性                |
| 可追溯   | 每条数据带来源、时间戳              |

### 3.4 指令协议设计

| 要点 | 说明                       |
| ---- | -------------------------- |
| 幂等 | 同一指令重复下发只执行一次 |
| 确认 | 外部系统接收后返回确认     |
| 超时 | 指令有超时时间             |
| 过期 | 过期指令不执行             |
| 签名 | 指令带签名，防伪造         |
| 审计 | 指令下发记录审计           |
| 回滚 | 指令可撤销                 |

### 3.5 没有合作方时的处理

**定义标准接入协议，用模拟器产生符合协议的数据。**

| 步骤 | 动作                         |
| ---- | ---------------------------- |
| 1    | 参考行业标准定义协议         |
| 2    | 定义数据契约（Schema）       |
| 3    | 模拟器按契约产生数据         |
| 4    | 接入层按契约校验数据         |
| 5    | 未来真实合作方按同一契约对接 |

**关键：协议先定，数据源可换。模拟器是第一个数据源，不是唯一数据源。**

### 3.6 参考的行业标准

| 标准                       | 用途                 |
| -------------------------- | -------------------- |
| MQTT                       | 车辆状态上报         |
| gRPC / HTTP                | 任务请求、控制指令   |
| Protobuf / JSON Schema     | 数据契约             |
| V2X BSM                    | 车辆基本安全消息     |
| Apollo / Autoware 消息格式 | 自动驾驶消息参考     |
| GB/T 国标                  | 国内自动驾驶数据标准 |

### 3.7 模拟器要模拟什么

模拟器不只是产生"假数据"，而是模拟一个外部自动驾驶系统：

| 模拟内容 | 说明                           |
| -------- | ------------------------------ |
| 车辆状态 | 位置、速度、电量按真实逻辑变化 |
| 任务响应 | 接收指令后状态变化             |
| 异常事件 | 模拟异常上报                   |
| 网络行为 | 模拟断连、延迟、重传           |
| 协议行为 | 按标准协议上报                 |

**模拟器是"外部系统的替身"，未来真实系统接入时，模拟器退场。**

## 五、插件进程内扩展设计

### 5.1 为什么进程内

| 维度       | 独立进程         | 进程内       |
| ---------- | ---------------- | ------------ |
| 部署复杂度 | 每个插件一个容器 | 宿主统一加载 |
| 资源开销   | 每插件独立内存   | 共享宿主内存 |
| 通信开销   | 跨进程           | 函数调用     |
| 启动速度   | 慢               | 快           |
| 调试难度   | 跨进程           | 同进程       |

**插件数量多时，独立进程不现实。进程内扩展是必然选择。**

### 5.2 进程内插件架构

```
┌─────────────────────────────────────────────┐
│              plugin-host                    │
│  ┌───────────────────────────────────────┐  │
│  │  插件注册表                            │  │
│  │  - 插件清单（plugin.json）             │  │
│  │  - 依赖解析                            │  │
│  │  - 生命周期管理                        │  │
│  └───────────────────────────────────────┘  │
│  ┌───────────────────────────────────────┐  │
│  │  插件实例                              │  │
│  │  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐    │  │
│  │  │插件A│ │插件B│ │插件C│ │插件D│    │  │
│  │  └─────┘ └─────┘ └─────┘ └─────┘    │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
```

### 5.3 插件接口

插件实现统一接口：

| 接口      | 作用           |
| --------- | -------------- |
| onLoad    | 加载时调用     |
| onUnload  | 卸载时调用     |
| onMessage | 收到消息时调用 |
| onTimer   | 定时调用       |
| getRoutes | 暴露 HTTP 路由 |
| getHealth | 健康检查       |

**插件不直接创建进程，由 plugin-host 调用。**

### 5.4 进程内基础保护

| 维度         | 做法                           |
| ------------ | ------------------------------ |
| 异常保护     | try-catch 包裹，崩溃不影响宿主 |
| 超时控制     | 消息处理超时终止               |
| 命名空间隔离 | 插件 ID 前缀                   |
| 版本隔离     | 每个插件独立版本               |

### 5.5 进程内插件的收益

| 收益     | 说明                       |
| -------- | -------------------------- |
| 部署简单 | 宿主一个容器，插件动态加载 |
| 资源省   | 共享宿主内存和连接         |
| 启动快   | 毫秒级加载                 |
| 调试易   | 同进程调试                 |
| 监控易   | 宿主统一采集               |

## 六、服务与层数分离

### 6.1 核心思想

**服务是逻辑单元，层是部署单元。同一服务可以在任意层部署，代码不变。**

| 概念     | 定义                                            |
| -------- | ----------------------------------------------- |
| 服务     | 逻辑功能，如 dispatch-core、ingest、data-writer |
| 层       | 部署位置，如接入层、处理层、决策层              |
| 服务实例 | 服务在某一层的具体运行实例                      |
| 层配置   | 声明某层启用哪些服务                            |

### 6.2 当前阶段部署

当前阶段只部署单层，所有服务集中运行。层配置预留三层结构，未来按需启用。

### 6.3 层配置

```yaml
layers:
  - name: access
    services: [ingest, data-writer, dispatch-core, observability, registry]
  - name: processing
    services: [ingest, data-writer, dispatch-core, observability, registry]
  - name: decision
    services: [ingest, data-writer, dispatch-core, observability, registry]
```

**层只决定启用哪些服务，服务代码不变。**

### 6.4 加层

后续要加层，只需在 `layers.yml` 中插入一段配置，服务代码零改动：

```yaml
layers:
  - name: access
    services: [...]
  - name: region          # 新加
    services: [...]
  - name: processing
    services: [...]
  - name: decision
    services: [...]
```

**加层只加配置，服务代码零改动。**

### 6.5 服务与层的关系

| 服务          | 接入层 | 处理层 | 决策层 |
| ------------- | ------ | ------ | ------ |
| ingest        | ✅     | ✅     | ✅     |
| data-writer   | ✅     | ✅     | ✅     |
| dispatch-core | ✅     | ✅     | ✅     |
| observability | ✅     | ✅     | ✅     |
| registry      | ✅     | ✅     | ✅     |

**同一服务在每层以不同配置运行，代码一份。**

## 七、调度算法设计

### 7.1 调度对象定义

**任务定义：**

| 字段          | 说明                          |
| ------------- | ----------------------------- |
| task_id       | 任务唯一标识                  |
| task_type     | 载客/巡检/物流/充电/维护/救援 |
| origin        | 起点                          |
| destination   | 终点                          |
| time_window   | 时间窗                        |
| priority      | 优先级                        |
| constraints   | 约束列表                      |
| service_level | 服务等级                      |

**车辆定义：**

| 字段         | 说明                       |
| ------------ | -------------------------- |
| vehicle_id   | 车辆唯一标识               |
| position     | 当前位置                   |
| status       | 空闲/执行中/充电/维护/离线 |
| battery      | 电量                       |
| capabilities | 能提供的服务类型           |
| constraints  | 车辆约束                   |

### 7.2 目标函数

| 目标               | 说明              |
| ------------------ | ----------------- |
| 最小化乘客等待时间 | 从下单到上车      |
| 最大化订单完成率   | 完成订单 / 总订单 |
| 最小化空驶率       | 空驶里程 / 总里程 |
| 最大化供需匹配率   | 匹配成功 / 总需求 |

**总目标 = 各目标加权求和，权重按场景配置。**

### 7.3 约束条件

**硬约束（必须满足）：**

| 约束         | 说明               |
| ------------ | ------------------ |
| 续航约束     | 电量足够完成任务   |
| 时间窗约束   | 能在时间窗内到达   |
| 服务能力约束 | 车辆能提供该服务   |
| 地理约束     | 在运营区域内       |
| 法规约束     | 该区域允许自动驾驶 |
| 状态约束     | 车辆状态可用       |

**硬约束过滤候选车辆集合。**

### 7.4 调度流程

```
任务到达
  ↓
硬约束过滤 → 候选车辆集合
  ↓
目标函数评估 → 每辆车的得分
  ↓
选择最优 → 生成调度指令
  ↓
签名 → 下发外部系统
```

### 7.5 算法插件化

| 插件              | 算法       | 维度        |
| ----------------- | ---------- | ----------- |
| nearest-dispatch  | 最近邻     | 空间        |
| batch-match       | 批量匹配   | 空间 + 全局 |
| priority-dispatch | 优先级调度 | 服务等级    |

**dispatch-core 负责任务分发，具体算法由插件实现。**

### 7.6 算法规格

| 算法              | 输入                | 输出       | 核心逻辑                |
| ----------------- | ------------------- | ---------- | ----------------------- |
| nearest           | 任务 + 候选车辆     | 最近车辆   | Haversine 距离排序      |
| batch-match       | 一批任务 + 一批车辆 | 匹配对     | 匈牙利算法 / 最小成本流 |
| priority-dispatch | 多任务 + 优先级     | 优先级排序 | 优先级队列 + 抢占       |

### 7.7 算法选择

| 场景     | 推荐算法   |
| -------- | ---------- |
| 实时单   | 最近邻     |
| 预约单   | 批量匹配   |
| 紧急任务 | 优先级调度 |

### 7.8 dispatch-core 与算法插件的关系

| 角色          | 职责                                         |
| ------------- | -------------------------------------------- |
| dispatch-core | 任务接收、约束过滤、算法调度、结果下发、签名 |
| 算法插件      | 接收候选车辆 + 任务，返回排序后的候选        |
| 算法选择      | 按任务类型 + 场景 + 配置选择算法             |
| 多算法协作    | 可串行（过滤+排序）或并行（投票）            |
| 算法切换      | 运行时切换，正在执行的任务用旧算法完成       |
| 算法回退      | 算法超时/失败时回退到 nearest                |

## 八、消息总线与多媒介

### 8.1 消息总线抽象

业务代码只依赖统一接口，不依赖 Kafka SDK：

| 接口      | 作用         |
| --------- | ------------ |
| connect   | 连接总线     |
| publish   | 发布消息     |
| subscribe | 订阅消息     |
| commit    | 提交消费位点 |
| health    | 健康检查     |

适配器：

| 适配器        | 媒介         |
| ------------- | ------------ |
| MqttAdapter   | MQTT         |
| KafkaAdapter  | Kafka        |
| MemoryAdapter | 内存（测试） |

### 8.2 数据流媒介

当前阶段数据流使用两种媒介：

| 段           | 媒介  | 理由         |
| ------------ | ----- | ------------ |
| 外部 → 接入 | MQTT  | 长连接、海量 |
| 内部         | Kafka | 可靠、可回溯 |

### 8.3 切换媒介

改配置 `MESSAGE_BUS=kafka` → `MESSAGE_BUS=pulsar`，业务代码零改动。未来可扩展 Pulsar、NATS、Redis、S3 适配器。

## 九、监控、日志、追踪

### 9.1 监控体系

| 层级     | 监控对象   | 指标                             |
| -------- | ---------- | -------------------------------- |
| 插件     | 每个插件   | 调用次数、延迟、错误率、资源占用 |
| 服务     | 每个服务   | QPS、延迟、错误率、饱和度        |
| 数据流   | 每段数据流 | 吞吐、延迟、积压、丢失           |
| 消息总线 | 每个总线   | 生产/消费速率、分区、消费者组    |
| 存储     | PG/Redis   | 连接、查询、命中率、容量         |
| 系统     | 全局       | 总车辆、总消息、总服务、总告警   |

### 9.2 日志体系

| 日志类型   | 内容           |
| ---------- | -------------- |
| 应用日志   | 服务运行日志   |
| 插件日志   | 插件运行日志   |
| 数据流日志 | 消息流转日志   |
| 错误日志   | 异常与错误     |
| 性能日志   | 慢查询、慢消费 |

日志统一格式，包含 `trace_id`、`span_id`、`service`、`plugin`、`layer`。

## 十一、安全性设计

**核心思路：从认证、输入验证、密钥管理建立安全基础。智能驾驶服务调度对安全要求极高，安全要内建，不是事后补。**

### 11.1 身份与认证

| 对象 | 认证方式        |
| ---- | --------------- |
| 车辆 | 证书 + 设备指纹 |
| 服务 | 基础认证        |
| 用户 | JWT             |
| 插件 | 权限声明        |

### 11.2 输入验证

- 所有入口校验输入。
- 防注入（SQL、命令、路径）。
- 防重放。
- 防篡改。
- 限流与熔断。

### 11.3 密钥管理

- 使用环境变量或 Secrets Manager。
- 不在代码中硬编码密钥。
- 密钥轮换。
- 最小权限密钥。

### 11.4 指令安全

- 调度指令带签名。
- 指令有超时时间。
- 指令有幂等标识。
- 指令下发记录审计。

### 11.5 数据安全

- 敏感数据加密存储。
- 传输加密。
- 访问控制。

## 十二、压力测试策略（以后再做）

**核心思路：当前阶段不做压力测试，但在设计和监控上预留能力，确保以后能顺利开展。**

### 12.1 现在不做什么

- 不做 5000、10 万、100 万、1000 万规模的压力测试。
- 不做长时间稳定性测试。
- 不做故障注入测试。

### 12.2 现在要做什么（预留）

| 预留项         | 目的                                             |
| -------------- | ------------------------------------------------ |
| 监控指标       | 预留 QPS、延迟、错误率、饱和度等指标             |
| 日志格式       | 预留 trace_id、span_id，便于以后压测分析         |
| 配置外置       | 车辆数、消息频率、并发数等从配置读，方便压测调整 |

| 消息总线可切换 | 方便对比不同总线在压力下的表现                   |
| 插件懒加载     | 方便控制变量，只启用需要的插件                   |

### 12.3 以后怎么做

- 用模拟器生成不同规模的数据。
- 用监控观察各层、各服务、各插件的指标。
- 用追踪定位瓶颈。
- 用对比实验评估不同调度算法、不同总线、不同层数的表现。
- 定义关键指标：乘客等待时间、空驶率、订单完成率、供需匹配率、高峰期表现。

## 十七、消息总线性能策略

| 方案         | 作用                               |
| ------------ | ---------------------------------- |
| 主题分层     | raw / aggregated / events 三层分离 |
| 选择性订阅   | 插件声明 filter，只收需要的数据    |
| 共享消费者组 | 相似插件共享组，减少扇出           |
| Redis 热路径 | 高频查询走 Redis，不压消息总线     |
| 批量消费     | max.poll.records 调优              |
| 按车辆分区   | 分区键为 vehicle_id，并行消费      |
| 插件懒订阅   | 未激活不占消费者名额               |
| 总线可切换   | 按场景选 Kafka/Pulsar/NATS/Redis   |

**核心规则：**

- 新插件默认订阅 `telemetry.aggregated`，不订阅 `telemetry.raw`。
- 新插件默认从 Redis 读状态，不直接消费消息总线。
- 新插件默认 `lazy: true`，只有明确需要常驻才设 `false`。
- 实时性 < 50ms 走 Redis Pub/Sub，不走 Kafka。
- 不同层、不同主题可以用不同总线。
- 切换总线只改配置，业务代码零改动。

### 阶段二：核心数据流服务

**阶段目标：** 打通"数据进来 → 数据存下"的主干道。

**实现思路：**

- simulator 产生 500 辆模拟车辆数据，通过 MQTT 上报。
- ingest 作为唯一外部出入口，订阅遥测，转发到消息总线。
- data-writer 作为唯一写库者，从消息总线消费，写入 PostgreSQL 和 Redis。
- 定义主题：telemetry.raw、telemetry.agg、events.commands、events.alerts。
- 所有服务通过消息总线抽象层通信，不直接依赖 Kafka SDK。
- 服务与层分离，同一服务可在任意层部署。

**具体任务：**

| 序号 | 任务                  | 怎么完成                                     | 产出                           |
| ---- | --------------------- | -------------------------------------------- | ------------------------------ |

## 二十、总结

本项目以"核心稳定、插件内嵌、服务层分离、数据统一、性能可控、文档同步、分层可扩、总线可换、调度多维、可观测性完整、安全内建、工程自动化"为总原则：

- **定位**：智能驾驶服务调度平台，接入外部自动驾驶系统，不造自动驾驶系统，不控制车辆。
- **核心**：10 个基础服务，每次全启，冻结维护。
- **插件**：进程内扩展，按 profile 选择，即插即用，自由迭代。
- **前端**：Vite + React 18 + TypeScript + TailwindCSS，现代审美。
- **数据流**：唯一规则，只有 Ingest 连外部，只有 Data-Writer 连库。
- **性能**：主题分层 + 选择性订阅 + Redis 热路径 + 批量消费，功能再多不压垮消息总线。
- **测试**：扁平化，按命名规则区分层级。
- **文档**：每个功能一个文档，按"功能名.V几.md"命名，版本递增，记录功能目标、基础实现、修改历史。
- **阶段**：六个阶段，每个阶段有明确目标、实现思路、具体任务、验收标准和文档产出。
- **分层**：服务与层数解耦，层数配置驱动，可随时加层，代码零改动。
- **总线**：消息总线抽象层，支持 MQTT/Kafka，可扩展其他适配器，切换只改配置，业务代码零改动。
- **调度**：调度算法以插件形式提供，覆盖空间、服务等级等维度。
- **可观测性**：覆盖插件、服务、数据流、消息总线、存储、系统，指标 + 日志。
- **CI/CD**：GitHub Actions，代码检查、单元测试、集成测试、构建、推送。
- **安全**：认证、输入验证、密钥管理、指令签名多层面内建安全。
- **压力测试**：当前不做，预留监控、日志、配置可调能力，以后再做。
